## 測試方法

使用 `/health` 端點進行測試，將同時請求數從 1 逐步提升至 15，藉此將 Lambda 冷啟動延遲與 LLM 處理時間分離。每個並行等級測試兩輪，每輪之間暫停 3 秒。回應時間超過 500ms 即判定為冷啟動。

```bash
uv run cold_start_test.py \
  --base-url "https://rhebly6ncnjdd5e25ifsgsliki0oloqj.lambda-url.ap-northeast-1.on.aws" \
  -m 15 -r 2 -p 3
```

## 主要發現

### 1. 基礎暖機實例數：約 2 個

冷啟動首次出現在 N=3（第二輪），表示測試開始前 Lambda 僅保持了 2 個暖機實例。

### 2. 冷啟動延遲：約 25-30 秒

冷啟動回應時間穩定在 25,000-30,000ms，原因包括：
- Python 運行環境初始化
- 大量套件載入（google-genai、fastapi、httpx 等）
- 應用程式啟動流程（TTL 快取暖機等）

### 3. 自動擴展行為

Lambda 逐步擴展，每次超出當前容量僅觸發 1-2 個新實例。擴展後的實例會在後續測試中保持暖機。

| 階段 | 並行數 | 暖機實例數 | 說明 |
|------|--------|-----------|------|
| 初始 | 1-2 | 2 | 近期流量的基礎暖機 |
| 擴展中 | 3-8 | 2→7 | 每次突發 +1 實例 |
| 持續擴展 | 9-12 | 9→10 | 前幾輪實例保持暖機，但超出容量仍觸發冷啟動 |
| 已充分擴展 | 13-15 | 12→15 | 累積足夠實例，不再冷啟動 |

### 4. 暖機回應延遲：53-320ms

暖機實例對 `/health` 的回應時間為 53-320ms，此為測試機器到 ap-northeast-1 的基礎網路往返時間。

## 建議

### 減少冷啟動時間

| 方法 | 影響 |
|------|------|
| 佈建並行（Provisioned Concurrency） | 為指定數量的實例消除冷啟動 |
| 延遲載入套件（Lazy imports） | 將初始化時間從 ~30s 降至 ~5-10s |
| 縮小部署包 | 加快程式碼下載速度 |
| SnapStart（如適用） | 基於快照的快速恢復 |

### 生產環境建議

目前基礎暖機實例僅 2 個，冷啟動延遲高達 30 秒。若並行使用者經常超過 2 人，建議設定**佈建並行 = 5-10**，以確保一般負載下不會出現冷啟動。
